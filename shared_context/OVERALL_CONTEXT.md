# 📖 Общий Контекст и Доменная Область Проектов (OVERALL_CONTEXT.md)

Данный документ содержит фундаментальное описание доменной области, используемых систем (TrackStudio, MS Project Server) и бизнес-правил учета трудозатрат для экосистемы продуктов **Colvir projects**.

---

## 1. Обзор Систем-Источников

### 1.1 TrackStudio (TS)
**TrackStudio** — корпоративная трекинг-система задач и трудозатрат.
- **Иерархия объектов**:
  - **Запрос (Parent Task)**: Главная задача по доработке/проекту (например, `#1726097`). Содержит общее описание, плановые сроки, текущего ответственного и статус.
  - **Подзадачи (Subtasks)**: Иерархическое дерево подзадач первого и второго уровня (категории работ: Анализ, Код, Тестирование, Документация, Управление, Внедрение и др.).
  - **Списания (Worklog / Затраченное время)**: Записи о фактически затраченном времени (в часах `ч.` или человеко-днях `ч.д.`), привязанные к конкретным подзадачам и сотрудникам с указанием даты списания.
- **Статусы и Вехи (Status Transitions)**:
  - Переход между статусами фиксируется историей операций (например, *"Сообщить предварительные условия"*, *"Передать в разработку"*, *"Передать на приемку"*, *"Сдать в ОПЭ"*).

### 1.2 MS Project Server (MSP)
**MS Project Server** — система календарно-сетевого планирования проектов.
- **WBS (Work Breakdown Structure)**: Иерархическая структура работ проекта с детализацией до этапов и конкретных задач.
- **Плановые трудозатраты**: Трудозатраты в человеко-днях/часах, распределенные по ролям (Аналитик, Разработчик, Тестировщик, Менеджер).
- **Связь с TS**: План из MS Project Server транслируется в TrackStudio либо в виде структурных этапов/задач, либо в виде консолидированных плановых показателей в комментариях/атрибутах запроса.

## 2. Бизнес-Правила План-Факт Анализа (Модель 5 Интервалов)

Для объективной оценки фактических трудозатрат и их сравнения с планом используется **Строгая 5-этапная модель жизненного цикла запроса**. Распределение фактических списаний подзадач по этапам выполняется строго по вехам дат операций из истории TS:

```
[T_0] ─── (1. ПО) ───> [T_po_boundary] ─── (2. ОА) ───> [T_dev_start] ─── (3. Реализация) ───> [T_accept_start] ─── (4. Приемка) ───> [T_release] ─── (5. Стабилизация) ───> ∞
```

### 1. Предварительный анализ (ПО) $[T_0, T_{po\_boundary})$
- **Граничная дата $T_{po\_boundary}$**: Дата операции *«Сообщить предварительные условия реализации»* / *«Согласовать предварительные условия»* / *«Вернуть на согласование окончательной оценки»*.
- **Состав работ**: Подзадачи с датой списания $t \le T_{po\_boundary}$ (Аналитик ПО, Конструктор ПО, Оценка ОТ, Консультации ПО, Управление ПО).
- **SLA-контроль**: На этап ПО действует регламентный срок **5 дней**. При превышении фиксируется нарушение SLA (`poSlaStatus = danger`).

### 2. Окончательный анализ (ОА) $[T_{po\_boundary}, T_{dev\_start})$
- **Граничная дата $T_{dev\_start}$**: Дата операции *«Передать в разработку»*.
- **Состав работ**: Подзадачи с датой списания $T_{po\_boundary} < t \le T_{dev\_start}$ (Требования, Постановки, План тестирования, Консультации ОА, Управление ОА).

### 3. Реализация (Код + ОТ) $[T_{dev\_start}, T_{accept\_start})$
- **Граничная дата $T_{accept\_start}$**: Дата операции *«Передать на приемку»* / *«Готовность к приемке»*.
- **Состав работ**: Подзадачи с датой списания $T_{dev\_start} < t \le T_{accept\_start}$ (Разработка кода, Сборка, Тиражирование, Тестирование ОТ, Баги разработки, Консультации при разработке).

### 4. Приемка банком $[T_{accept\_start}, T_{release})$
- **Граничная дата $T_{release}$**: Дата операции *«Сдать в ОПЭ»* / *«Внедрение»*.
- **Состав работ**: Все подзадачи от передачи на приемку до показа/сдачи Банку (Приемка работы, исправление замечаний Банка).

### 5. Стабилизация / ОПЭ $[T_{release}, \infty)$
- **Состав работ**: Все подзадачи, списанные после сдачи в ОПЭ (Внедрение, Сопровождение ОПЭ, баги на ПЭВМ/Проде).

## 3. Обработка Свернутых Строк и Фоллбэков (defaultPhase)

Если подзадачи в TrackStudio свернуты в категории первого уровня и индивидуальные даты списаний недоступны из текущего DOM:
- Алгоритм использует интеллектуальное сопоставление по **`defaultPhase`**:
  - `Аналитика` / `Конструктор` -> ПО (`po`)
  - `Планирование` / `Методика` -> ОА (`oa`)
  - `Разработка` / `Тестирование` / `Сборка` / `Документация` -> Реализация (`dev`)
  - `Приемка` -> Приемка (`accept`)
  - `Внедрение` / `Стабилизация` / `ОПЭ` -> Стабилизация (`stab`)

---

## 4. Архитектурные Требования к Коду

1. **Защита от двойного счета (Double-Counting Prevention)**: Исключение дублирования часов при одновременном сканировании родительских категорий и дочерних подзадач.
2. **Производительность**: Минимизация задержек при парсинге большого DOM дерева TrackStudio.
3. **Автономность и Надежность**: Поддержка On-Demand парсинга (в расширении) и автономной фоновой генерации (в дашбордах).
